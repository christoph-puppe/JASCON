CycloneDX Attestations (OWASP, ECMA-424)データとしての標準。クレームと反対クレームに対応付けられた要求事項、作成者と有効期限を持つ証跡、署名者を伴う確約（affirmation）。正規化 JSON に対するオブジェクト単位の署名で、インデントの変更後も有効リスクオブジェクトも、テーラリングの記録も、言語マップもない。証跡の添付ファイルにハッシュがない。署名は JSON 形式にしか存在しない：XML スキーマと protobuf 定義には署名を置く場所がない。署名者にも確約にも日付がない。拡張は名前と値の文字列で、そのレジストリは任意
CISO Assistant (intuitem)ツール内：管理策に紐づくリスクシナリオ、適用宣言書 (SoA) のエクスポート、承認者・日付・有効期限付きのリスク受容、有効期限付きのセキュリティ例外、監査ログ。ライブラリフォーマット内：200 を超えるフレームワーク、参照管理策、リスクマトリクス、集合論に基づくマッピング、オブジェクトごとの translations マップリスク受容、例外、適用宣言書はアプリケーション内にとどまり、外に出るのはライブラリフォーマットではなくバックアップのエクスポートを通じてのみ。署名はない：重複排除のためのバイト列ハッシュのみ。ライブラリの更新で既存の評価が書き換わりうる。要求事項に付随するチェックのロジックがない。インポーターは未知のライブラリキーを無視する
SCAP、XCCDF、OVALXML によるチェックリストとチェック言語。Tailoring ファイルは、ベンダーのベンチマークを編集せずに変更できる。override は権限者、時刻、理由を記録する。タイトルと説明は言語ごとに繰り返し記述できる。データストリームには署名と副署ができるリスクの記録がない。期日、有効期限、免除の型がない。収集した項目にハッシュがない。個々のテーラリング変更に作成者がなく、重大度を理由なしに引き下げられる。署名済みストリームのインデントを変えると署名が壊れる。適合するチェックは OVAL と OCIL で、任意の言語のスクリプトは OpenSCAP の拡張を通じてしか実行できない。外部の名前空間の要素は、たまたまスキーマが手元にある場合にしか検査されない
規制当局のフォーマットJSON Schema 付きの JSON による FedRAMP の統合ルール。YAML による BSI C5:2026。OSCAL のカタログとプロファイルによる Grundschutz++ と ISM発行者ごとに方言があり、それぞれがモダリティ、期限、適用範囲を独自の方法で構造化している。C5 はドイツ語版と英語版を別ファイルで配布。Grundschutz++ は語彙を、どのバリデータも読まない props に保持している
マッピングのセマンティクスNIST IR 8477 の関係スタイル。Secure Controls Framework の STRM。OWASP OpenCREIR 8477 が定義するのは関係であり、ファイルフォーマットではない。SCF はマッピングをスプレッドシートと PDF で公開し、OSCAL にエクスポートするのはカタログのみ。OpenCRE はハブ・アンド・スポーク型の要求事項グラフであり、カタログフォーマットではない
in-toto と SCITT来歴、検証サマリー、テスト結果、SBOM のための精査済み predicate を持つ署名付きの証明。署名付きステートメントに対する IETF の透明性サービス管理策や要求事項を証明する in-toto の predicate はない。SCITT は透明性のためのアーキテクチャであり、コンプライアンスモデルではない
Heimdall Data Format、OCSF、SARIFチェックとスキャンの結果チェックが何を見つけたかを運ぶもので、標準が何を要求するかではない
NIST IR 8286リスク登録簿とリスク詳細記録のスキーマリスクから管理策の選択へのエッジがない
OpenControl、Compliance MasonryYAML による標準とコンポーネントの説明文2023 年以降、目立った活動がない
ISO/IEC 27001 と 27002、IEC 62443、PCI DSS標準そのもの公式の機械可読版がない。SCF と CISO Assistant に第三者による表現がある

JASCON がこれらから取り入れたもの

JASCON の大部分は新しいものではありません。以下の各機能には、近接フォーマットに先例があります。

JASCON の機能最も近い先行技術
ステートメントごとの構造化されたモダリティGrundschutz++ の法助動詞の語彙。FedRAMP ルールのキーワード。OpenSSF OSPS Baseline
言語マップとしての本文CISO Assistant のライブラリフォーマットの translations マップ。XCCDF で繰り返し記述されるタイトルと説明に付く xml:lang
所属関係としてのベースラインOSCAL のプロファイル。XCCDF のプロファイル
閉じた操作リストとしてのテーラリングOSCAL プロファイルの alter と set-parameter。XCCDF の refine-value
フレームワーク間の型付きマッピングNIST IR 8477。Secure Controls Framework の STRM。OSCAL 1.2 のマッピングモデル。Gemara のマッピング文書
型付きでスキーマに拘束される拡張CISO Assistant 内の型付きカスタムフィールド。OSPS Baseline のように、Gemara の閉じたスキーマを絞り込む CUE プロファイル。名前空間付きだが型のない OSCAL の props。外部の名前空間にあり、緩く検証される XCCDF の要素
コンポーネントから指摘事項までの連鎖OSCAL のライフサイクルモデル。CycloneDX の宣言（declarations）
要求事項に対する署名付きの証明CycloneDX の確約と、正規化 JSON に対する署名（ECMA-424）。署名と副署が付いた SCAP データストリーム。in-toto の DSSE エンベロープ
リスクの記録事後的なものとしての OSCAL の risk アセンブリ。Gemara のリスクカタログ。CISO Assistant 内のリスクシナリオとリスク受容。NIST IR 8286
管理策から分離されたベンダーの助言OSCAL のコンポーネント定義。ベンダーのベンチマークに手を加えない XCCDF の Tailoring ファイル
承認者付きで記録された例外権限者、時刻、理由を持つ XCCDF の override。CISO Assistant のセキュリティ例外。OSCAL 上の FedRAMP の逸脱 props

どの近接フォーマットにも、組み合わせとしては見つからなかったもの

  • オブジェクトごとに 2 つのダイジェスト。1 つは配布されたバイト列に対するもの、もう 1 つは正規化されたコンテンツに対するもので、これにより証明が再パッケージ後も有効であり続けます。
  • モダリティの半順序。テーラリングはこれに照らしてチェックされ、緩和は記録された Deviation を経由しなければなりません。
  • 管理策の選択に結び付いたリスクの記録。これにより、どのリスクにも基づかない要求事項が計算で求められます。
  • フェイルクローズする拡張：拡張はどの計算を変えるかを宣言し、それを理解できないツールは停止しなければなりません。

この主張がどこまで成り立つか

4 つのいずれにも部分的な先例があります。この主張は組み合わせに関するもので、その強さは調査の確かさを超えるものではありません。最も近いのは Gemara と CycloneDX Attestations であり、どちらのコミュニティの読者も、なぜ JASCON は自分たちのフォーマットを拡張しないのかと問うでしょう。ハンドブックの付録 F.10 がそれに答えています。証明に関するギャップは小さなものです。in-toto には要求事項を証明する predicate がなく、JASCON の証明を predicate として表現すれば、既存の検証者のエコシステムに届くことになります。利用者と監査人にとって重要な 10 の機能は、トップページで比較しています。
