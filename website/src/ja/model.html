モデル

11 のオブジェクト型と、それぞれが置き換えるもの

カーネルが保持するのは、3 つの国家フレームワークを実測して必要と判明したものだけで、それ以外は何も含みません。このページでは、カーネルをひととおり説明します。規範となるテキストは仕様書です。すべての数値を含む詳細版はハンドブックです。

01 最小のオブジェクト

完結した 1 つの要求事項

これで 1 つのオブジェクトの全体です。props もファセットもなく、周囲を囲む文書もありません。ハンドブックがこれを最初の例に使っているのは、オーストラリアの ISM の拡張部分全体が、これ以上のものを必要としないからです。

  • id は、発行機関自身のドメイン配下の URI です。文字列として比較され、取得されることはないため、外部から遮断されたネットワークでも検証が機能します。
  • version と、マニフェスト内の 2 つのダイジェストが履歴を担います。ISM は同じ目的のために、2,202 個の改訂用 props を手作業で維持しています。
  • statements がリストなのは、条項が実際に存在するからです。Grundschutz++ には、条項を参照可能にするためだけに存在する、入れ子になった 347 個の疑似管理策があります。
  • modality と obligated-parties はステートメントに置かれます。1 つの要求事項で、運用者を MUST で、顧客を SHOULD で拘束できます。
  • prose は、言語タグからテキストへのマップです。

02 オブジェクト型

どの型も、公開されたカタログが必要としたから存在する

リリース済みの 1.0.0 には 9 つの型があります。Risk と Check は 10 番目と 11 番目の型で、2.0.0 のリリース候補に含まれます。右の欄は、その型が OSCAL 1.x や一般的な慣行から何を引き継ぐかを示しています。

内容：何が求められるか

Requirement

1 つの管理策、ルール、または基準を、識別子付きステートメントのリストとして表します。各ステートメントは、モダリティ、義務を負う当事者、型付きパラメータ、本文を持ちます。ガイダンスや目的もステートメントであり、そのモダリティは unspecified です。あるいは、フレームワーク固有のファセットに置かれます。

引き継ぐものカタログの管理策とその parts。props の label、alt-identifier、sort-id。

RequirementSet

所属関係だけを表し、それ以外は何も表しません。Set は、要求事項または他の Set を順序番号付きで列挙します。章、ファミリー、ベースライン、成熟度レベル、機密区分はすべて Set であり、1 つの要求事項が複数の Set に属することもできます。

引き継ぐものグループ、解決済みプロファイルによるベースライン、そして ISM の 5,301 項目からなる適用性マトリクス。

Tailoring

選択と、8 種類の操作からなる閉じたリストです。各操作は、要求事項、ステートメント、パラメータという識別子で対象を指定します。何も複製されません。解決は決定的な 1 回の処理で完了します。グローバルな識別子があるためマージ規則は不要であり、存在しません。

引き継ぐものプロファイルとプロファイル解決の仕様。FedRAMP CR26 に見られる、クラスごとのインラインの変種。

Mapping

クロスウォークの 1 本のエッジを、9 つのフラットなフィールドで表します。ソース、ターゲット、任意のステートメント範囲、関係、方向、確度、論拠、来歴、証跡です。関係コードは NIST IR 8477 に従い、他者のカタログに付加するコンテンツ用に supplements が加わります。

引き継ぐものOSCAL 1.2 の管理策マッピングモデル。クロスウォークのスプレッドシート。

組織：なぜ適用範囲に入るのか

Risk 2.0.0 候補

ISO/IEC 27001 の 6.1.2 と 6.1.3、BSI Standard 200-3、NIST SP 800-30 がいずれも求める記録です。シナリオ、所有者、状態、名前の付いた尺度上のレベルとして表す格付け、4 つの対応の選択肢のうちの 1 つ、そして対応を担う条項からなります。スコアリング手法はカーネルの外に置かれます。Risk は、評価され、対応の選択肢が選ばれた時点で、要求事項を正当化するものになります。

引き継ぐものスプレッドシートとしてのリスク登録簿と、文書としての適用宣言書 (SoA)。後者は risk-coverage が算出します。

システム：何が導入され、何が見つかったか

Component

製品、サービス、ポリシー、プロセス、またはシステムです。システムとは、メンバーを持つコンポーネントです。認可境界は、コンポーネント上の識別子付きオブジェクトです。境界がなければ、何も主張されません。

引き継ぐものコンポーネント定義と、SSP のシステム記述。

Implementation

1 本のエッジです。「このコンポーネントは、この要求事項を（必要ならこのステートメントを）、この方法で満たす」という関係を表します。責任は provider、customer、shared、inherited のいずれかです。継承のエッジは、上流のコンポーネントと、依拠する認可を明示しなければなりません。これにより、IaaS 上の PaaS 上で動く SaaS を、連鎖の 1 段ずつ検証できます。

引き継ぐものSSP の実装済み要求事項（implemented requirements）と、コンポーネント定義の管理策実装（control implementations）。この 2 つは同じことを二重に述べていました。

Assessment

誰が、何を、どのように、いつ確認し、どの結果とどの証跡が得られたかを表します。手法は、登録済みのファセットで記述します。

引き継ぐもの評価計画と評価結果。

Finding

要求事項またはステートメントに対するギャップです。状態、暦を明示した期日付きの対応措置、そして Deviation（逸脱）を持ちます。Deviation は、何かが緩和または受容される場面のすべてで使われる、1 つの状態機械（調査中、保留中、承認済み、撤回済み）を持つ 1 種類の型付きレコードです。

引き継ぐものPOA&M と、それぞれが同じ状態機械を符号化していた 4 つの FedRAMP 拡張。

署名

Attestation

オブジェクトのセマンティックダイジェスト、コンテンツマニフェストのダイジェスト、そして人が署名したレンダリング済み文書のダイジェストを、DSSE エンベロープの中で結び付けます。機械がチェックした内容と、認可権限者が署名した内容が、気付かれないまま食い違うことはありません。

引き継ぐものデータとの関係を誰も検証できない、署名済みの PDF。

機械：要求事項をどう判定するか

Check 2.0.0 候補

コレクターが報告するファクトの型付き契約と、12 個の比較演算子によるフラットな論理積で、合否を判定します。コレクターのコードはファセットに置かれます。この形式に収まらないものは手動チェックのままです。記録された判定はバリデータが再計算し、証跡ファイルは SHA-256 で命名されます。

引き継ぐもの文章で書かれた監査手順。たとえば CIS Ubuntu 24.04 Benchmark の 291 個の自動化ルールは、人が読まなければならないテキストとして届きます。設計とライブデモ。

ベンダー：供給者が何を推奨するか

アドバイスパック 型ではない、2.0.0 候補

マニフェストで発行元、パック、リリースを示し、オブジェクトが Component だけからなるバンドルです。ベンダーの推奨事項は、その Component 上のケイパビリティであり、要求事項、条項、テキスト、推奨パラメータ値を持ちます。パックをインポートしても、セットが既に保持しているオブジェクトは一切変わりません。推奨事項は、ユーザー自身の Implementation が引用するまで、何の効力も持ちません。

引き継ぐものコンポーネント定義の用途のうち、残す価値のある唯一のもの。ベンダーは検討用のテキストを提供するだけで、管理策や評価を変更することはできません。パックの仕組み。

03 拘束力

法助動詞には順序があり、テーラリングはその順序に照らしてチェックされる

3 つのコーパスが、同じフィールドに行き着いています。Grundschutz++ の modal_verb（1,006 件）、FedRAMP CR26 の force、そして ISM のスタイルガイドです。JASCON では、これは半順序を持つカーネル定義のコードです。

義務
unspecifiedmayshouldmust
禁止
unspecifiedshould-notmust-not
制限（ドイツ語の DARF NUR）
maymay-only

矢印の向きに沿った移動は単調であり、自由に行えます。矢印に逆らう移動は緩和であり、チェーン間の移動は軸の変更です。発行機関が公開する Tailoring はどちらも行えますが、利用者側の Tailoring では、どちらの場合も承認者付きの Deviation を記録する必要があります。要求事項の除外は単なる選択であり、Deviation は不要です。ベースラインは除外によって構成されるからです。

パラメータには型がある

文字列、整数、正規形の 10 進数、真偽値、日付、URI、コードがあり、コンテナとして選択、リスト、範囲があります。期間は、経過時間か、暦を明示した暦上の期間のいずれかです。営業日で示す期限は、暦がなければ意味をなさないからです。本文中の {param:name} トークンは宣言済みのパラメータに解決されなければなりません。また、リストは JSON 配列であり、読み手が分割方法を知っていなければならない文字列には決してなりません。

04 拡張

すべてのオブジェクトにある 2 つのメンバーが、それ以外のすべてを担う

3 つの国家カタログで数えた 22,000 個の props のうち、70% 以上はカーネルの仕組みを模倣しています。所属関係、順序付け、履歴、別名、条項構造です。残りには契約が与えられます。

facets

標準ライブラリに 7 個

ファセット名は、バンドルのマニフェストで厳密なバージョンとダイジェストによって固定された JSON Schema に解決されます。ファセットの記述子は、それが何を変えるか（評価、テーラリング、選択、レンダリング）を宣言します。ツールは、固定されたスキーマに照らしてペイロードを検証します。意味を持つファセットのうち自身が実装していないものに出会ったツールは、処理を停止して理由を出力します。

理由：現在は、1 つの未知の prop に出会った 3 つのツールが 3 通りの異なる動作をし、しかも 3 つとも適合を主張しています。

annotations

ダイジェストの対象外

ツールの管理情報やレンダリングのヒントのためのフラットなマップです。たとえば、トラッカーの ID、Web 用の名前、リンク禁止フラグなどです。annotations は定義上、あらゆるコンプライアンス計算の対象外であり、セマンティックダイジェストにも含まれません。そのため、仕様に適合する実装がそこから意味を読み取ることはありません。

理由：ツールには独自のメモを置く場所が必要ですが、その場所が検証されない第 2 の語彙になってはならないからです。

05 完全性

オブジェクトごとに 2 つのダイジェスト

公開物はバンドルです。オブジェクト、固定されたファセットスキーマ、レンダリング、そして 1 つのコンテンツマニフェストからなります。証明はマニフェストの隣に置かれます。署名されたものが、自分自身の署名を含むことはできないからです。

判定パッケージダイジェストセマンティックダイジェスト意味
Full Match一致一致証明されたパッケージそのもの。
Semantic Match不一致一致承認された内容を再パッケージしたもの。検証者はその旨を報告する。
Tamper任意不一致内容が承認されたものと異なる。

06 適合性

3 つのティア、いずれも裏付けを伴う

ティアの主張は、公開されている適合性コーパスに照らして検証されます。コーパスでの結果を伴わない主張は、ただのデータシートにすぎません。

ティア約束する内容
Core全型のスキーマ検証、閉域環境での動作、パッケージダイジェスト、ローカルでの参照解決、未知の要素すべての保持。意味に関わる計算は行わない。
Portableフェイルクローズのゲートを伴う、固定スキーマに対するファセット検証、セマンティックダイジェスト、決定的なテーラリング解決、規則に適ったバンドル構成、リスクカバレッジ、記録されたすべてのチェック判定の再計算。
Authority公開に伴う義務：管理された安定識別子、再編のたびの別名と系譜の記録、オブジェクトごとの両ダイジェスト、非推奨化のライフサイクル。

07 ベンダーの助言

推奨するのはベンダー、合格基準を決めるのは利用者

ベンダーは、自社製品をどう堅牢化するかを知っています。アドバイスパックは、その知識を、それが役立つ要求事項の隣に置く形でグラフに取り込みます。ADVICE-1 から ADVICE-11 までの 11 のルールが、このファイルを助言の範囲にとどめます。

  • Component のみ。Requirement、Tailoring、Check、Assessment を含むパックは拒否されます。パック内のすべての id は発行元自身のオリジン配下にあるため、利用者のオブジェクトを置き換えることはできません。
  • 推奨事項はケイパビリティである。推奨事項は、要求事項、条項、テキスト、推奨パラメータ値を示します。product-version は、その助言が製品のどのバージョン向けかを示します。
  • 採用は利用者のエッジで行う。利用者の Implementation が <component-id>#<capability-id> を引用し、製品は利用者のシステムのメンバーでなければなりません。それまでは、ケイパビリティは主張にすぎず、それに基づく計算は一切行われません。
  • ベンダーのマニフェストがインポートの記録になる。マニフェストは、そのバイト列の SHA-256 で命名され、利用者のセットに残ります。同じファイルが二重にインポートされることはなく、別のリリースは以前のリリースが持ち込んだものだけを置き換え、インポート後に編集された助言は報告されます。
  • 申告のみ、証明付き、実証済み。ツールが発行元を「実証済み」と表示するのは、ベンダーの証明がマニフェストを結び付けており、その署名が利用者の信頼する鍵で検証できる場合だけです。誰もチェックしていない証明は、そのとおりに表示されます。

設計済み {{ n.advice_vectors }} 件のテストベクトルと、公開テスト鍵で署名された作例のパック 1 つがあります。パックを公開したベンダーはまだなく、条項レベルのフィールドは架空の例ファイル 1 つだけに基づいています。限界について。

08 OSCAL 1.x のユーザー向け

すべての移行先

OSCAL はこの取り組みの出発点であり、JASCON が読み書きする形式です。カタログのバンドルは OSCAL 1.2.2 にエクスポートされます。OSCAL に対応する構成要素がないものは、名前空間付きの props に載せて運ばれ、インポート時に元に戻ります。

1 時間読んでから、バンドルを開く

ハンドブックの第 2 章は、実在する最小のオブジェクトから順にカーネルを組み立てていきます。アプリでは、同じオブジェクトを SP 800-53、CSF 2.0、ISM、Grundschutz++ で確認できます。

1 時間でわかるコア はじめに
