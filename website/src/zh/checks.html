检查 · 内核 2.0.0，发布候选版

当评估者是一台机器

一个只以 0 或 1 退出的扫描器，会隐藏自己的阈值、忽略裁剪，也不留下任何可供复查的东西。Check 公开采集器必须报告的事实，以及作出判定的比较。运行记录携带了观测到的内容，因此任何人都能根据记录重新计算判定。

02 设计

采集器负责观测，判定条件负责判定

界线划在工具之间必须达成一致的地方。两个符合规范的工具，给定同一个 Check 和同一个观测值，会返回相同的判定。凡是可以在诚实的工具之间有所不同、而又不改变判定的东西，都留在内核之外。

分面，位于内核之外

采集器

一个 shell 脚本、一个 Ansible 任务或一次 API 调用，随 Check 一起携带，使该检查的摘要覆盖确切的代码。它输出一个观测值，不作任何判定。

内核：事实契约

观测值

具名、有类型的事实，例如 sshd.maxauthtries：整数。采集器报告的是生效值，并已解析默认值。缺失的键表示“查找过，但未找到”。

内核：十二种比较算子

判定条件

一个扁平的合取式，例如 at-most {param}。期望值是一个字面量或该要求的一个参数，因此由绑定该参数的 Tailoring 设定及格线。

内核：check-verdict

判定

满足、不满足、无定论或不适用：它是 Check、观测值和已绑定参数的纯函数。校验器会重新计算每一个已记录的判定。

裁剪后的参数会重新调校检查

在 Tailoring 中把 max-auth-tries 从 6 收紧到 4，昨天观测到的 5 就会从“满足”变为“不满足”。没有任何一行代码改变，实施方也无法自行设定及格线。

判定要重新计算，从不直接采信

Assessment 的记录行中保存着观测值本身。第二方据此对判定条件求值并加以比较。已记录的结果若与计算结果不同，即为校验错误。

记录显示观测到了什么

一条未通过的记录行写着 sshd.ciphers matches-not ".*-cbc"，观测到的是一个包含 aes128-cbc 的列表。换作退出码，就只有一个 1。

04 比较算子

十二种，外加一份被排除内容的清单

这个集合是有意保持精简的。不符合的检查仍为人工检查，并计入统计。

  • 判定条件是一个合取式。没有 OR，没有 NOT，也没有嵌套；一个值的多个备选用 one-of 表示，否定则体现在成对的算子中。
  • 没有算术运算，也不在两个事实之间进行比较。计数和推导是采集器的工作。
  • 组合方式是强 Kleene 逻辑的 AND：一个确定的失败即决定结果，失败永远不会被别处的未知值掩盖。
  • 未绑定的参数得出“无定论”。绝不会代入默认值。
  • at-most 绝不绑定向上收紧的参数，这样收紧参数就不可能放宽检查。
  • 涉及多个资源的检查，只有在每个适用资源都通过时才算通过。每个资源都会被求值，不会在第一次失败后跳过其余资源，判定还附带数量和占比：“200 个适用的存储桶资源中有 12 个不满足（6%）”。
算子作用对象成立条件
equals单个值该值等于期望值；小数按数值比较
not-equals单个值该值不同于期望值；事实缺失时为无定论
one-of单个值该值在列表中
at-least at-most整数、小数大小比较；小数绝不按浮点数处理
present absent任意事实该键在观测值中存在，或不存在
includes-all列表所列的每个值都出现
excludes-all列表所列的值均未出现
subset-of列表观测到的每个值都在所列范围内
matches matches-not字符串、代码整个值与某个 I-Regexp 模式匹配，或者没有任何模式匹配

为什么允许使用正则表达式

手册拒绝使用表达式语言，因为那样一来，两个符合规范的工具可能返回两个不同的判定。Python、.NET 和 JavaScript 恰恰在人们最常用的构造上存在分歧：\d、\w、锚点、标志、环视。因此选用的方言是 I-Regexp（RFC 9485），它由 IETF 为互操作性而制定，并被 JSONPath 采用。

内核在 RFC 之外还规定了什么

  • 模式匹配整个值。^ 和 $ 是普通字符。
  • 限制：每个模式 256 个字符、1,000 个状态，每个值 4,096 个字符。超出限制时，该记录行的结果为无定论。
  • 不使用宿主引擎。每个实现都按照 RFC 9485 公布的语法自行解析，并以无回溯方式匹配，因此任何模式都无法让校验器卡死。
  • 仍保留一项依赖，并已明确说明：Unicode 类别 \p{..} 从宿主的数据库中读取（待办事项 59）。

05 证据

每一环都可离线验证

证据是内容清单旁边的一个目录。每个文件都以其字节的 SHA-256 命名。脱敏在计算哈希之前进行，原始输出是单独的文件，因此按保留期限删除文件后，记录依然可以验证：校验器会将该文件报告为“不予提供”。

Attestation

绑定 Assessment 的语义摘要。

Assessment 记录行

以内联方式保存观测值，因此该摘要也覆盖了观测值。它同时通过引用和摘要指明所用的 Check：检查一旦改变，就是另一个检查。

证据记录

写明检查、采集器、被检对象、开始与结束时间以及退出状态，并携带同一观测值的摘要。

原始输出

stdout 或 API 响应，各以摘要标识，并附媒体类型、大小和脱敏标志。

06 实测适配度

510 条规则中有 481 条符合声明式形式

比较算子集合是先起草、后测量的，测量对象是两个公开的检查语料库：ComplianceAsCode 中面向 Ubuntu 24.04 的四个 CIS profile（510 条规则），以及 kube-bench 的 CIS 1.12 检查（103 项自动化、28 项人工）。

类别规则数（共 510 条）
符合其中 23 条仅在采集器解析生效值、并以标志集合报告模式位时才符合481
需要算术运算计数、唯一性、与当前时间比较12

需要版本排序2
需要 I-Regexp 之外的正则表达式0

普查显示了什么 实测，适配与否凭人工判断

  • 比较这一侧很小，逻辑都在采集这一侧。在 126 个手写的 OVAL 定义中，各 state 使用相等比较 99 次、使用模式 23 次、使用大小比较 41 次。
  • 在 491 个正则表达式中，有 23 个位于比较一侧。这 23 个全部落在 I-Regexp 范围之内，或可机械地改写。
  • 在 kube-bench 的 21 个 OR 检查中，有 16 个的含义是“标志缺失，或标志等于某值”。一个报告生效值的采集器可以把它们变成一次比较。

它纠正了什么

起草时的集合中没有“不等于”。普查在 OVAL 的 state 中发现了 2 处，在 kube-bench 的所有目录中共发现 85 处；而对于数值，没有其他算子能表达这一点。它于 11月12日作为第十二种比较算子加入。不符合的 29 条规则仍为人工检查。

向作者提出的问题2026年11月12日的决定
晋升规则要求普查所涵盖的三个权威机构中有两个对某种类型进行了编码。而没有任何一个编码了检查。该规则针对目录权威机构不发布的类型新增了一个条款：要么有公认标准要求该记录，要么它是经两个已统计的开放实现证实的既定做法；另外两项检验仍须满足；它须随主版本引入。Risk 依据第一个分支纳入，Check 依据第二个分支纳入。
运行记录行：内核字段还是分面？内核字段。判定是计算，而分面从不定义计算。
Check 能否不附带其所引用的要求而单独发布？可以。针对不得再分发的目录的检查包，可以独立通过校验。
现在落地，还是等待云 API 普查？Check 随 2.0.0 正式生效。
除“每个资源”之外，是否还要另一个量词？不需要。每个资源都被求值并记录，报告失败占比，且检查判为不通过。
是否增加第十二种比较算子 not-equals？已增加。
