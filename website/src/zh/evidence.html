04 局限

尚未证明的内容

以下是截至 {{ facts.measured.date }} 的未决问题。每一项同时也是外部贡献比维护者本人的工作更有分量的地方。

没有第三方用户 未决

2026年11月10日的一次搜索显示，除其自身仓库外，没有任何地方提到 JASCON。没有权威机构用它发布内容，也没有厂商读取它。已实测的转换结果以及在已发布目录中发现的缺陷，无需采用该格式即可使用。

两个校验器出自同一位作者 未决

Python 参考实现和 PowerShell 孪生实现均由项目作者在 AI 辅助下依据同一批资料编写。二者的独立性仅限于编程语言和运行时。该关口衡量的是规范能否确定一个实现，而不是衡量一个陌生人用一个周末能做出什么。

路径覆盖不等于值到达 未决，待办 41

覆盖报告统计的是具有已声明目标位置的源路径。每个值是否到达，只在一个语料库（NIST 示例系统）上用台账逐值追踪过，该台账跟踪每个源值在转换器中的去向：835 个叶值中，258 个被携带（232 个原样复制，26 个经由具名规则转换），104 个标识符按设计舍弃，473 个去向不明：既没有目标位置，也没有说明原因。其余十个语料库尚未测量。

第一个 Risk 语料库停留在初始状态 未决

OSCAL 的风险数据没有责任人、没有单一等级，也没有接受日期。从中转换得到的风险无法离开 identified 状态，因此在真实的转换数据上，风险覆盖会把每条要求都显示为未覆盖。带有已处置风险的覆盖情况仅在示例捆绑包上展示。

Check 的结构仅基于两个平台定型 未决

Check 类型的适配度只在 Linux 主机和 Kubernetes 上统计过。没有统计过任何针对云 API 的检查，仓库中没有任何东西运行采集器，完整示例是针对一个桩（stub）运行的。在统计的 510 条规则中，有 29 条不适合声明式形式，仍需人工处理。查看完整现状。

2.0.0 是候选版本，而非正式发布 未决

已没有待决事项，两个校验器在候选版本的全部 {{ n.vectors }} 个测试向量上均为绿色。打标签是作者要做的一步，目前尚未进行。在此之前，已发布的版本是 1.0.0，2.0.0 的结构仍可能变化。

并非每个 1.0.0 捆绑包都是 2.0.0 捆绑包 已决定

在 rc.2 之前，2.0.0 Schema 接受 1.0.0 所接受的一切。从 rc.3 起，偏离的登记日期必须是一个日期，措施的截止日期必须是类型化的时间点或时长。在这两个字段中任一使用自由文本的 1.0.0 捆绑包都必须进行转换。随附的五个捆绑包和示例文件夹全部符合要求。含 Unicode 类别的模式遵循其运行机器上的 Unicode 数据库，因此一个较晚才分配的码位可能在两台机器上得出两种判定；需要唯一判定的作者应写出字符范围。

建议包仅以一个示例文件为依据 已设计

没有任何目录权威机构发布厂商建议。对于此类数据，晋升规则要求：要么有一项标准规定必须具备此记录，要么有两个内容经过统计的开放实现。建议包两者都没有。能力上的条款级字段仅以 NIST 示例中的一个虚构组件定义为依据，其中有三条建议、两个条款级条目和两个建议参数值；产品版本字段则没有任何经过统计的依据。两者均由作者在违背该规则的情况下决定纳入内核，规范也如实记录了这一点。尚无厂商发布过建议包；建议包构建器可以导入 OSCAL 组件定义，NIST 自己的示例在导入时不会丢失建议包能够容纳的任何内容，但还没有任何由厂商发布的组件定义经过它的处理。这项普查仍有待完成。

随附示例中的已知缺陷 未决，待办 46 和 55

示例证明仅作说明之用：其主体摘要与任何示例对象都不匹配。Assessment 的方法载荷尚未按其锁定的分面 Schema 进行校验，而仓库中现有的三个都会校验失败。

同类格式领先的两处 未决，待办 65 和 66

2026年11月13日的比较发现了两处。Deviation 记录了它的登记时间和批准人，但没有到期时间；而 CISO Assistant 中的安全例外有到期日期，OSCAL 中的风险有期限。裁剪操作不记录其自身的作者：弱化需要一条经批准的 Deviation，其他每项变更只能通过包含它的 Tailoring 来归属作者，而 CISO Assistant 会记录每一项变更。两者均已作为第 65 和 66 项列入待办清单，各自都需要作者作出决定。

治理只靠一个人 未决

手册描述了一个联邦式注册中心和一位标准库管理人。两者都还不存在。目前只有一位以个人身份工作的维护者、一份公开的决策登记册，以及一致性测试语料库。

带计数的完整队列：规范反馈待办清单。条目凭证据进入，并通过决策登记册中的一条记录退出。

05 现有技术

同类格式缺少什么

分两轮完成。前五行于 2026年11月13日对照指定版本的 Schema 或代码进行了核查：OSCAL 1.2.3、Gemara 1.6.0、CycloneDX 1.7.2、CISO Assistant，以及 XCCDF 1.2 与 SCAP 1.4。其下各行来自 11月10日的调研，资料取自公开仓库；无法访问一手站点时，则取自二手来源。没有转换任何同类格式的数据，因此表中每一格说明的是格式本身提供了什么，而不是某个部署用它做了什么。

格式涵盖内容缺少内容
OSCAL (NIST)目录（catalog）、profile、组件定义、系统安全计划、评估计划与评估结果、POA&M，以及自 1.2.0 起的控制措施映射。从控制措施到带哈希的证据文件的完整链条；风险上的期限；一个无法修改目录的厂商模型风险只存在于评估结果和 POA&M 中，从不与它本可作为依据的选择并列。profile 变更不记录作者。没有任何结构能承载第二种语言。没有原生签名：上游拒绝了内联签名（issue 245），只剩下字节哈希。扩展 prop 带有一个无人校验的命名空间字符串，而为 SP 800-53 编写的核心约束也会约束其他框架（#2118、#2112）
Gemara (OpenSSF)分层目录，涵盖指南、控制措施、威胁、风险和能力；带有类型化关系、强度和置信度的映射文档；证据带摘要的评估日志；以 CUE 编写的 Schema。被 FINOS Common Cloud Controls 和 OpenSSF OSPS Baseline 采用没有第二种语言的正文。发现项或豁免没有截止日期或到期时间。没有实施记录：模型为其指定了一个层级，却没有提供 Schema。接受风险时没有批准人或日期。签名覆盖的是已发布捆绑包的字节，由工具在 Schema 之外完成。Schema 是封闭的：CUE profile 可以收窄它们，但不能新增字段。策略和风险 Schema 被标记为实验性
CycloneDX Attestations (OWASP, ECMA-424)以数据表示的标准；映射到主张与反主张的要求、带作者和到期时间的证据、带签署人的确认声明（affirmation）。基于规范化 JSON 的逐对象签名，重新缩进后依然有效没有风险对象，没有裁剪记录，没有语言映射表。证据附件不带哈希。签名只存在于 JSON 形式中：XML Schema 和 protobuf 定义中都没有它的位置。签署人和确认声明都不带日期。扩展是名称/值字符串，其注册表是可选的
CISO Assistant (intuitem)在工具中：与控制措施关联的风险场景、适用性声明导出、带批准人、日期和到期时间的风险接受、带到期日期的安全例外、审计日志。在库格式中：200 多个框架、参考控制措施、风险矩阵、基于集合论的映射、每个对象的 translations 映射表风险接受、例外和适用性声明都留在应用程序内；它们通过备份导出离开应用程序，而不是通过库格式。没有签名：字节哈希只用于去重。库更新可能改写已有的评估。要求上没有附加检查逻辑。导入器会忽略它不认识的库键
SCAP、XCCDF、OVAL以 XML 表示的检查单和检查语言。Tailoring 文件可在不编辑厂商基准的情况下修改它；override 记录授权方、时间和理由；标题和描述按语言重复；数据流可以签名和会签没有风险记录。没有截止日期、到期时间或豁免类型。采集项不带哈希。单项裁剪变更没有作者，而且可以在不给出理由的情况下降低严重程度。重新缩进已签名的数据流会破坏签名。符合一致性要求的检查只有 OVAL 和 OCIL；任意语言的脚本只能通过 OpenSCAP 扩展运行。外部命名空间中的元素只有在恰好有 Schema 可用时才会被校验
监管机构格式FedRAMP 的合并规则以 JSON 及 JSON Schema 提供；BSI C5:2026 以 YAML 提供；Grundschutz++ 和 ISM 以 OSCAL 目录和 profile 提供每个发布者一种方言，各自以自己的方式组织情态、期限和适用性。C5 以单独的文件分别提供德文和英文；Grundschutz++ 把它的词汇保存在没有任何校验器读取的 prop 中
映射语义NIST IR 8477 的关系样式；Secure Controls Framework 的 STRM；OWASP OpenCREIR 8477 定义的是关系，而不是文件格式。SCF 以电子表格和 PDF 发布其映射，只把它的目录导出为 OSCAL。OpenCRE 是一种中心辐射式的要求图，而不是目录格式
in-toto 与 SCITT带有经审核谓词（predicate）的签名证明，用于来源出处、验证汇总、测试结果和 SBOM；基于已签名声明的 IETF 透明性服务没有任何 in-toto 谓词用于证明控制措施或要求。SCITT 是一种透明性架构，而不是合规模型
Heimdall Data Format、OCSF、SARIF检查和扫描的结果它们承载的是检查发现了什么，而不是标准要求什么
NIST IR 8286风险登记册和风险详细记录的 Schema没有从风险到控制措施选择的边
OpenControl、Compliance MasonryYAML 格式的标准和组件叙述自 2023 年以来没有实质性活动

这一主张的适用范围

这四项各自都有部分先例。该主张针对的是它们的组合，其可靠程度取决于调研的充分程度。Gemara 和 CycloneDX Attestations 是最接近的同类格式，来自这两个社区的读者都会问，JASCON 为什么不去扩展他们的格式；手册在附录 F.10 中作了回答。证明方面的差距很小：in-toto 没有用于证明要求的谓词，而若将 JASCON 证明表达为这样一个谓词，便可接入现有的验证器生态。对用户和审计人员重要的十项特性，在首页上进行了比较。
