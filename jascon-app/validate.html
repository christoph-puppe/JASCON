Trusted keys for signatures

An attestation may name an envelope with a signature (DSSE, Ed25519). Whose key to trust is yours to say and never comes from the bundle: a JSON map of signer URI to public key in hex. With a map here the check runs in verification mode: an envelope is judged against the signer's key, and a Tailoring counts as authority-proven only through an envelope that verifies. Without one, an envelope is checked for what it binds and reported as unverified. Public keys are no secret; the map is kept in this browser.

Two reports say who decided and when. The first lists where an author, the day of a decision or the day of an authorization is not stated (AUTHOR-1 to AUTHOR-4). Whether that is a failure is your programme's policy: with the switch on, each of its lines is an error; with it off, a note. The second lists every review date that has passed on the day asked about (REVIEW-1). An empty day means today, in UTC. An overdue review is never an error: the Deviation or Risk still holds until someone acts.

⊕Compose two sets

What would happen if the active set and another set were used together. Where both pin a facet in the same major line, the higher version wins and the payloads of both are checked again under it. What does not fit is reported and never picked silently: two major lines, a version that is not semver, a payload that fails under the winner, one id at two versions, and one id and version with two meanings. Nothing is written.

?What is checked, and what is not

Checked, each rule ported from validate_core.py and run against its conformance vectors:

The manifest: its shape, and that it pins the kernel its content needs. Every object: that it matches exactly one kernel type, that an optional list is absent instead of empty, that statement ids are unique, that every {param:} token is declared, that a facet keyed by statement names statements that exist.

Integrity: both digests of every object and the digest of every pinned file against the manifest. An object edited in this app is reported as a note, because the export writes a new manifest.

References: every reference that must resolve inside the bundle does, with the right type; Set membership has no cycle; a mapping's scope names statements that exist.

Tailorings: two operations on one target; a weakening without a Deviation at consumer tier; a parameter value of the wrong kind. Facets: every payload against the standard descriptor or the pinned schema; an unregistered facet fails.

Risks and scales: RISK-1 to RISK-14 with the coverage of the selected requirements, SCALE-1 to SCALE-4 with the matrix.

Signatures: the envelope an attestation names is checked for what it binds, and against the signer's key when you supply trusted keys. Every attestation of the set is looked at, those beside the manifest and any the manifest lists; an envelope that is named and not there is an error.

Attestations: every Attestation of the set is held to what it binds (Appendix B.1.7). Each subject is compared with the objects the manifest lists: it matches, it differs (the object of that id has another semantic digest), or it is absent. The manifest it names is this one, a pack manifest the set keeps, or another. All subjects match and the manifest is this one or a kept pack's: Full Match. All match and the manifest is another: Semantic Match, reported. Anything else is a failure while the Attestation is active, and reported when it is a draft, deprecated or withdrawn. A set that was changed in this app is compared with the bundle an export would write now, and the result says so. The lines are the reference validator's.

Advice packs: what a pack may hold (ADVICE-1 to ADVICE-3), capabilities and the edges that cite them (ADVICE-4 to ADVICE-7), and the pack manifests the set keeps under packs/sha256/ against their names and against the objects of the set (ADVICE-8 to ADVICE-10). For every pack the check says how far its publisher is established: proven only with a signature that verifies under a trusted key, attested and not verified without keys, claimed otherwise. ADVICE-11 is asked when a pack is imported, on the Home page.

Who decided, and when: where a consumer's Tailoring, a Risk, a Finding or an Implementation names no author, where a decided Deviation states no day and an authorization no date (AUTHOR-1 to AUTHOR-4), and which review date of an approved Deviation or a managed Risk has passed (REVIEW-1). The lines are the reference validator's for the same set and day; its --require-authors is the switch of the first view, its --as-of the day.

The composition of two sets has a view of its own.

Not checked: conditional-apply instances. The engine is ported and passes its vectors, but no bundle has a place to carry an instance, here as in the reference validator. The bytes of a bundle on disk (line ends, files the manifest does not list) are judged by the Python validator only. In every case of doubt run jascon/scripts/validate_core.py on the exported bundle; it is the reference.
